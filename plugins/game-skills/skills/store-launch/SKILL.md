# Store Launch

혼자 또는 소규모로 앱을 만드는 사람이 처음 스토어에 출시할 때 겪는 일을 끝까지 끌고 간다.
사용자는 개발은 할 줄 알지만 스토어 정책 용어와 콘솔 화면은 낯설다고 가정한다. 기본 전제는 한국의 1인 개인사업자, Unity 프로젝트, 결제는 Unity IAP, 광고는 AdMob, 통계는 Firebase Analytics다. 전제가 다르면 그에 맞게 조정하고, 어디가 다른지 사용자에게 말한다.

## 이 스킬이 막으려는 실패

실제 출시 준비에서 반복해서 나온 문제들이다. 아래 절차는 전부 이것을 막기 위한 것이다.

- 사용자가 뜻을 모르는 용어로 결정을 요구받는다. ("Kids Category 방향만 정해 주세요")
- 할 일이 대화 속에 흩어져서 사용자가 전체 그림과 진행 상황을 잃는다.
- 에이전트가 기억에 의존해 규격이나 정책을 단정했다가 콘솔에서 거부된다. (스크린샷 크기)
- 방침과 스토어 신고 내용이 실제 앱 동작과 다르다. (SDK가 몰래 보내는 통계)
- 에디터에서 본 것과 실기기 동작이 달라 사용자가 오해한다. (가격이 "준비 중", 다른 스토어 문구)
- 출시 직전에야 어색한 화면이나 틀린 문구가 눈에 띈다.
- 작업 중 커밋 안 된 남의 변경을 덮어쓰거나, 의도하지 않은 설정 변경이 커밋에 섞인다.

## 진행 순서

요청이 일부만 해당하면(예: "방침만 만들어 줘") 필요한 단계만 한다. 다만 3번의 기록 파일이 없으면 먼저 만든다.

### 1. 점검: 지금 어디까지 되어 있나

프로젝트를 읽고 "출시 가능한 상태인가"에 먼저 답한 뒤 근거를 표로 준다. 점검 방법은 `references/audit.md`를 따른다.

- 결론을 첫 문장에 쓴다. ("TestFlight 배포까지만 된 상태이고 정식 출시는 아직 안 됩니다")
- 저장소에서 확인한 것과 콘솔 안이라 볼 수 없는 것을 구분한다.
- 빌드 파일(IPA, AAB)이 있으면 `scripts/inspect_build.py`로 실제 들어간 권한, 개인정보 선언, 접속 서버를 뽑아 추측을 증거로 바꾼다.

### 2. 결정: 사용자만 정할 수 있는 것

출시 범위와 계정에 관한 결정을 한 번에 모아 묻는다. 목록과 설명 문구는 `references/decisions.md`에 있다.

- 결정마다 **무엇인지 쉬운 말로**, 선택지, 각 선택의 결과, **되돌릴 수 있는지**, 추천을 함께 준다. 용어만 던지지 않는다.
- 되돌릴 수 없는 선택(Kids Category 승인, iPad 지원, 상품 ID와 유형)은 그렇다고 분명히 말한다.
- 사용자가 "그게 뭔데?"라고 되묻는다면 설명이 부족했던 것이다. 다시 물을 필요가 없게 처음부터 풀어 쓴다.

### 3. 기록: 체크리스트와 로그를 먼저 만든다

`assets/launch-checklist.md`와 `assets/launch-log.md`를 프로젝트의 `docs/`로 복사해 채운다. 이후 출시와 관련된 변경이 있을 때마다 **같은 턴 안에서** 두 파일을 갱신한다.

- 체크리스트: 할 일 전체와 상태. ✅ 완료(저장소나 검증으로 확인됨), ⬜ 미완료, ❓ 확인 필요(콘솔 안이라 볼 수 없음).
- 로그: 정한 것과 이유, 바꾼 파일, 알아낸 것, 자주 찾는 값(주소, ID), 작업 중 사고.
- 체크리스트 맨 위에 "지금 남은 일"을 순서대로 둔다. 사용자가 "그다음 뭐 해?"를 묻지 않아도 되게 한다.
- 사용자가 다음에 기억하지 못할 것을 전제로 쓴다. 에이전트 메모리에 저장하지 말고 저장소 파일에 남긴다. 프로젝트의 에이전트 지침 파일(AGENTS.md, CLAUDE.md)이 있으면 "출시 관련 변경은 이 두 문서에 적는다"는 규칙을 추가한다.
- `scripts/checklist_status.py`로 남은 항목 수와 목록을 뽑을 수 있다.

### 4. 작업: 코드 쪽과 콘솔 쪽

코드 쪽은 직접 고치고 검증한다. 콘솔 쪽은 사용자가 해야 하므로 단계별로 안내한다.

| 주제 | 참고 문서 |
|---|---|
| 두 스토어 공통인 일과 따로 하는 일 | `references/platforms.md` |
| 인앱결제 | `references/iap.md` |
| 광고 (AdMob) | `references/ads.md` |
| 개인정보 처리방침, 개인정보 신고, 이용 통계 | `references/privacy.md` |
| App Store Connect, TestFlight | `references/apple.md` |
| Google Play Console | `references/google-play.md` |
| 한국 개인사업자 관련 | `references/korea.md` |
| Unity 프로젝트 설정과 빌드 | `references/unity.md` |

필요한 문서만 읽는다. 결제만 붙인 앱에서 광고 문서를 읽을 필요는 없다.

한 플랫폼을 먼저 출시하는 경우가 많다. 그때는 `references/platforms.md`로 지금 하는 일이 다른 플랫폼에도 쓰이는지, 나중에 따로 해야 하는지를 사용자에게 알려 준다. 체크리스트 틀도 공통 / iOS / Android로 나뉘어 있으니, 미룬 플랫폼의 항목은 지우지 말고 "다른 쪽 출시 뒤에 진행"이라고 적어 둔다.

콘솔 안내의 원칙:

- 사용자가 콘솔 화면의 글을 붙여 넣으면 칸마다 **필수 / 하면 좋음 / 안 해도 됨**으로 나누고 각각 이유를 한 줄로 단다. 붙여 넣을 값의 초안은 `assets/listing.md` 틀로 파일에 만들어 준다.
- 메뉴 이름과 위치는 자주 바뀐다. 기억으로 적은 것은 "기억 기준"이라고 밝히고, 못 찾으면 화면을 보여 달라고 한다.
- **크기, 개수, 기간 같은 규격은 콘솔 화면에 적힌 값이 우선이다.** 스크린샷이나 자산을 만들기 전에 업로드 칸에 표시된 허용 규격을 사용자에게 확인받는다. 확인 없이 만들었으면 추정이라고 말한다.
- 누를 버튼과 넣을 값을 번호 순서로 준다. "상품 정보를 채우세요"가 아니라 어디에 무엇을 넣는지 쓴다.

### 5. 대조: 말한 것과 앱이 하는 것이 같은가

방침, 스토어 개인정보 신고, 스토어 문구는 실제 앱 동작과 일치해야 한다. `references/privacy.md`의 대조 절차를 따른다.

- SDK 공식 설명만 믿지 말고 패키지 코드에서 네트워크 전송을 찾는다. 결제 라이브러리나 엔진 서비스가 통계를 보내는 경우가 있다.
- `scripts/scan_wording.py`로 앱 문구와 스토어 문구에서 다른 스토어 이름과 금지 표현을 찾는다. 다른 플랫폼 이름이 한쪽 스토어 빌드에 보이면 반려 사유가 된다.
- 문구가 코드가 아니라 이미지에 구워져 있을 수 있다. 화면에서 본 글이 검색에 안 잡히면 이미지와 생성 도구를 의심한다.

### 6. 제출 전 점검

- **화면 훑어보기**: 출시 범위에 들어가는 화면을 실제로 그려서 본다. 새로 붙인 기능일수록 기존 디자인과 어긋난 곳이 있다. 사용자가 발견하기 전에 먼저 본다.
- **실기기 확인표**: 구매, 삭제 후 재설치와 복원, 광고 시청과 보상, 방침 링크, 언어 전환. 에디터 검증은 이것을 대신하지 못한다. 표는 `references/apple.md`와 `references/google-play.md`에 있다.
- **빌드 확인**: 빌드가 어느 커밋으로 만들어졌는지, 버전 번호가 맞는지 확인한다. 커밋 해시를 물으면 전체 해시를 준다.
- 스크린샷은 `scripts/fit_screenshot.py`로 크기와 투명도를 검사한다.

## 사용자와 대화하는 방식

- 답을 먼저, 근거는 그다음. 표를 좋아하는 사용자에게는 표로 준다.
- 사용자가 한 일과 에이전트가 한 일을 구분해 "누가" 칸을 둔다. 사용자만 할 수 있는 일(계정, 콘솔, 결제 정보, 법적 신고)을 대신 한 것처럼 쓰지 않는다.
- 확인한 것과 확인하지 못한 것을 나눠 말한다. "에디터에서 가짜 응답으로 검증했고 실기기에서는 아직"처럼 범위를 밝힌다.
- 법률 판단(신고 전 판매가 되는지, 동의가 필요한지)은 단정하지 않는다. 아는 범위를 말하고, 누구에게 무엇을 물어야 하는지와 기다리지 않고 안전하게 진행하는 순서를 준다.
- 비슷한 이름의 항목은 섞어 쓰지 않는다. "상품 생성"과 "상품 정보 입력"은 다른 일이다. 이미 끝난 일을 다시 하라고 한 것처럼 들리면 사용자가 혼란스러워한다.

## 작업 안전

- 커밋 안 된 변경이 있는 파일은 `git checkout`이나 덮어쓰기로 되돌리지 않는다. 고치기 전에 `git status`로 남의 작업이 섞여 있는지 본다.
- 커밋 전에 변경 목록을 훑어 의도하지 않은 파일(에디터가 바꾼 설정, 임시 캡처, 비밀 키)이 섞였는지 확인하고, 뺀 것이 있으면 이유와 함께 알린다.
- 인터넷에 공개되거나 되돌리기 어려운 일(웹 페이지 게시, 스토어 업로드, 심사 제출, 계정 설정 변경)은 실행 전에 확인받는다. 한 번 받은 허락을 다른 일로 넓히지 않는다.
- 빌드는 푸시된 커밋으로 만들어지는 경우가 많다. 검증이 끝나기 전에 푸시하면 깨진 코드로 빌드가 돈다.
- 프로젝트에 검증 절차나 에이전트 지침이 있으면 그것을 따른다. 이 스킬은 그 위에 얹는 것이다.

## 스킬을 갱신할 때

정책과 콘솔 화면은 계속 바뀐다. 참고 문서의 수치와 메뉴 이름은 작성 시점의 것이므로, 실제 화면과 다르면 화면을 따른다.

출시 준비를 하면서 참고 문서와 다른 점을 발견하면(거부된 규격, 바뀐 메뉴, 새로 생긴 필수 항목, 처음 겪은 반려 사유) 프로젝트의 로그에 적고, 일이 일단락됐을 때 사용자에게 "스킬의 참고 문서에도 반영할까요?"라고 묻는다. 반영할 때는 해당 참고 문서를 고치고 `references/platforms.md`의 갱신 기록에 날짜와 내용을 한 줄 남긴다.

Android 쪽 문서는 내부 테스트 빌드까지만 해 보고 쓴 것이다. Android 프로덕션 출시를 진행하게 되면 이 스킬을 갱신할 가장 좋은 기회이므로, 겪은 순서대로 `references/google-play.md`를 채운다. 글로벌 출시도 마찬가지로 `references/korea.md` 옆에 국가별 문서를 추가한다.
