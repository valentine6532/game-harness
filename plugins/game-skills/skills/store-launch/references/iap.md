# 인앱결제

결제 코드 구현 자체는 구현 스킬(예: implement-in-app-purchases)의 영역이다. 이 문서는 출시 관점에서 확인할 것을 다룬다.

## 출시 전에 갖춰져 있어야 하는 것

| 항목 | 이유 | 확인 방법 |
|---|---|---|
| 상품 ID가 코드와 콘솔에서 같음 | 다르면 그 상품만 가격이 안 뜸. 콘솔에서는 만든 뒤 못 바꿈 | 기획 데이터나 코드의 ID 목록과 콘솔을 대조 |
| 상품 유형이 맞음 (소모품, 비소모품, 구독) | 만든 뒤 못 바꿈 | |
| 구매 복원 | Apple 필수. 기기를 바꾸거나 다시 설치한 사람이 혜택을 되찾는 길 | 버튼이 있는지, 앱 시작 때 자동 확인도 하는지 |
| 승인 대기 구매 처리 | 가족 공유의 "구매 요청"은 승인 전에 혜택을 주면 안 됨 | 승인 전·후 동작 |
| 혜택 저장 후 거래 확정 | 저장에 실패했는데 거래를 확정하면 돈만 나가고 혜택이 없음 | 저장 → 확정 순서인지 |
| 보호자 확인 | 어린이가 쓰는 앱이면 구매·복원 시작 전에 | 게이트가 걸린 위치 |
| 가격 표시 | 스토어에서 받아 온 값을 그대로. 코드에 박은 가격을 보여 주면 국가별로 틀림 | |
| 플랫폼별 안내 문구 | iPhone에서 "Google Play", Android에서 "App Store"가 보이면 안 됨 | `scripts/scan_wording.py`와 코드의 분기 |

## 에디터에서 되는 것과 안 되는 것

에디터는 스토어에 접속할 수 없다. 그래서:

- 가격 자리에 "준비 중" 같은 대체 글이 뜬다. 고장이 아니다.
- 에디터는 실제 기기 플랫폼이 아니라서 다른 플랫폼용 경로를 탈 수 있다. iPhone 화면을 흉내 내는데 Android 문구가 보이는 식이다. 사용자가 보고 놀라지 않게 미리 말하고, 가능하면 흉내 내는 기기 플랫폼을 기준으로 경로를 고르게 한다.
- 가격이 채워진 화면이 필요하면(심사용 스크린샷) 테스트 가격을 넣어 그리는 검증용 화면을 쓴다.
- 구매 흐름 자체는 가짜 스토어 응답으로 검증할 수 있지만, 그것은 "코드가 응답을 올바로 처리한다"는 것까지만 보여 준다.

사용자에게 결과를 말할 때 "에디터에서 가짜 응답으로 확인함"과 "실기기에서 확인함"을 구분한다.

## 시험 환경

| 플랫폼 | 돈이 나가지 않는 방법 |
|---|---|
| iOS | TestFlight로 설치한 빌드는 자동으로 시험 환경. 결제 창에 표시가 뜸 |
| Android | 내부 테스트 트랙으로 설치하고 라이선스 테스터 계정으로 결제 |

비소모품은 한 번 사면 그 계정에 남는다. 구매 과정을 여러 번 보려면 테스터 계정이 더 필요할 수 있다.

## 가격이 안 뜰 때 보는 순서

1. 유료 앱 계약(Apple) 또는 결제 프로필(Google)이 활성 상태인가
2. 상품 ID가 코드와 같은가
3. 상품 정보가 다 채워져 판매 가능한 상태인가
4. 스토어를 통해 설치한 빌드인가 (TestFlight, 내부 테스트)
5. 번들 ID와 패키지명이 콘솔의 앱과 같은가

## 나중에 생각할 것

- 환불 시 혜택 회수: 스토어의 서버 알림을 받을 서버가 있어야 한다. 없으면 환불돼도 혜택이 남는다. 심사에는 문제없다.
- 결제 라이브러리가 자체 통계를 보내는지: `audit.md`의 숨은 전송 찾기 절차로 확인하고 방침에 반영한다.
