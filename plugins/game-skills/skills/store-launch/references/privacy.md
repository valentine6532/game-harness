# 개인정보 처리방침, 스토어 개인정보 신고, 이용 통계

원칙은 하나다. **방침, 스토어 신고, 앱의 실제 동작이 같은 내용이어야 한다.** 방침을 예쁘게 쓰는 것보다 앱이 실제로 무엇을 보내는지 정확히 아는 것이 먼저다.

## 1. 앱이 실제로 보내는 것 조사

`audit.md`의 "숨은 전송 찾기"까지 마친 뒤, 아래 표를 채운다.

| 구분 | 항목 | 어디로 | 근거 |
|---|---|---|---|
| 기기 안에만 저장 | 닉네임, 진행 기록, 설정, 구매 식별자 | 기기 | 저장 코드. 서버 전송 코드가 없는지 |
| 이용 통계 | 앱 식별자, 기기 정보, 대략적 지역, 자동 기록, 직접 정의한 이벤트 | 통계 서비스 | 이벤트 코드, SDK 설정 |
| 광고 | 기기 식별자, IP와 대략적 위치, 광고 노출 기록, 진단 | 광고 서비스 | SDK의 개인정보 선언 |
| 결제 라이브러리 통계 | 설치·세션 식별자, 기기 정보, 구매 시도 | 라이브러리 제공사 | 패키지 코드 |
| 결제 | 결제 수단 | 스토어 | 운영자는 받지 않음 |

주의할 표현:

- "외부로 전송되지 않는다"고 쓰려면 기기 백업을 생각한다. 저장 위치가 기기 백업에 포함되면 "기기의 백업 기능을 켠 경우 백업에 포함될 수 있다"고 덧붙인다.
- 통계의 지역 정보는 보통 IP로 추정한 것이다. "국가 수준"이라고 줄여 쓰지 않는다.
- 통계 SDK는 직접 정의한 이벤트 말고도 앱 실행, 세션, 구매 같은 것을 자동으로 기록한다.
- "보호자 확인 뒤에만 외부 페이지가 열린다" 같은 문장은 광고 클릭까지 생각한다. 광고를 누르면 스토어나 웹이 열린다.

## 2. 방침 작성

`assets/site/privacy.html`(한국어), `privacy-en.html`, `privacy-ja.html`을 복사해 고친다. `【 】`로 표시된 곳이 채울 자리다.

한국 기준으로 들어가야 하는 항목:

| 항목 | 틀에서의 위치 |
|---|---|
| 처리 목적과 처리 항목 | 2 |
| 아동 관련 조치 | 3 |
| 보유 기간과 파기 방법 | 4 |
| 처리 위탁, 제3자의 수집, 국외 이전 (받는 자, 항목, 국가, 시기와 방법, 보유 기간, 거부 방법과 불이익) | 5 |
| 자동 수집 장치와 거부 방법 | 6 |
| 이용자와 법정대리인의 권리와 행사 방법 | 7 |
| 안전성 확보 조치 | 8 |
| 보호책임자 연락처, 구제 기관 | 9 |
| 방침 변경, 시행일 | 10, 맨 위 |

작성 규칙:

- 운영자 이름, 연락처 이메일, 시행일은 사용자에게 묻는다. 시행일은 "방침이 효력을 갖기 시작하는 날, 보통 처음 게시하는 날"이라고 설명한다.
- 언어마다 페이지를 나누고 서로 가는 링크를 둔다. 앱은 현재 언어의 페이지를 연다.
- 앱 동작에 따라 달라지는 전제(통계 보존 기간, SDK 설정, 다른 플랫폼에서 아직 안 한 조치)는 파일 맨 위 주석에 적는다.
- 법률 전문가 검토를 대신하지 않는다고 사용자에게 말한다.
- 미국에 출시하면 아동 보호법에 따라 운영자 주소와 전화번호도 필요하다. 국가를 넓힐 때 다시 본다.

## 3. 작성 후 대조

방침의 문장을 하나씩 코드와 맞춰 본다. 특히:

- 처리하는 회사 목록에 빠진 곳이 없는가
- "하지 않는다"고 쓴 것(추적, 맞춤 광고, 서버 저장)이 빌드에서도 사실인가
- 보호자 확인이 걸려 있다고 쓴 기능에 실제로 걸려 있는가
- 지원 페이지의 안내(기록 복구, 구매 복원)가 실제 동작과 같은가. 실기기에서 확인하지 않은 것은 사용자에게 그렇게 말한다

## 4. 게시 (Firebase Hosting)

Firebase Hosting은 정적 파일을 올려 두는 웹 호스팅이다. 무료 요금제(Spark)는 카드 등록이 없어서 한도를 넘어도 청구되지 않고 그날 페이지만 멈춘다. 사용자가 비용을 물으면 이렇게 설명한다.

저장소 루트에 `assets/site/firebase.json`을 복사하고, `.firebaserc`에 프로젝트 ID를 넣는다. `cleanUrls`가 켜져 있어서 `privacy.html`이 `/privacy`로 열린다.

```
npm i -g firebase-tools          # 한 번만. 설치 프로그램
firebase login                   # 브라우저에서 로그인. 사용자가 직접
firebase deploy --only hosting   # 폴더의 파일을 올림
```

- 명령만 던지지 말고 각 줄이 무엇을 하는지 설명한다.
- `firebase login`은 사용자가 해야 한다. 설치와 업로드는 허락을 받으면 대신 할 수 있다. **업로드는 인터넷에 공개되는 일이므로 실행 전에 확인받는다.**
- 설치 직후 모듈을 못 찾는 오류가 나면 다시 실행해 본다. 계속되면 재설치한다.
- 준비 확인: `firebase login:list`에 계정이 보이고 `firebase projects:list`에 프로젝트가 `(current)`로 표시된다.
- 올린 뒤 주소마다 열리는지 확인한다. 캐시 때문에 예전 내용이 한 시간쯤 보일 수 있다.

## 5. 앱과 콘솔에 연결

- 앱: 방침 주소를 한 곳의 상수로 둔다. 보호자 메뉴처럼 어른이 여는 화면에 링크를 둔다. 링크를 여는 부분은 검증에서 바꿔 끼울 수 있게 해서 검사 중 브라우저가 열리지 않게 한다.
- Apple: 개인정보 처리방침 URL. 언어별로 따로 넣을 수 있다.
- Google: 주소 하나.

## 6. 스토어 개인정보 신고 답안 만들기

1번의 표를 스토어의 분류로 옮긴다. 초안을 `assets/listing.md` 틀의 개인정보 칸에 적어 준다.

AdMob, Firebase Analytics, 통계를 보내는 결제 라이브러리가 들어 있는 앱의 전형적인 답안:

| 데이터 유형 | 용도 | 근거 |
|---|---|---|
| 기기 ID | 타사 광고, 분석 | 광고 SDK, 결제 라이브러리 |
| 대략적인 위치 | 타사 광고 | 광고 SDK (IP 기반) |
| 제품 상호 작용 | 분석, 타사 광고 | 통계, 광고 |
| 광고 데이터 | 타사 광고 | 광고 SDK |
| 구입 내역 | 분석 | 통계의 자동 구매 기록, 결제 라이브러리 |
| 충돌, 성능, 기타 진단 데이터 | 분석, 앱 기능 | 광고 SDK |

계정이 없고 추적 허용을 요청하지 않는 앱이면 "신원에 연결됨"과 "추적에 사용됨"은 아니요다. 이 표는 출발점이고, 각 SDK 제공사가 공개한 스토어 신고 안내와 대조하라고 사용자에게 말한다.

## 7. 통계 설정에서 챙길 것

- 이벤트에 닉네임이나 저장 내용을 넣지 않는다.
- 광고 개인화에 통계 데이터를 쓰지 않게 한다. 실행 중 설정만으로는 앱이 켜진 직후의 짧은 구간이 비므로 기본값도 막는다(iOS는 Info.plist, Android는 매니페스트).
- 통계 보존 기간 설정을 방침의 문구와 맞춘다. 콘솔 안의 값이라 사용자가 확인해야 한다.

## 8. 고칠 때

SDK를 추가하거나 빼거나 버전을 올릴 때, 광고·통계 설정을 바꿀 때 방침과 스토어 신고를 다시 맞춘다. 방침을 고치면 시행일도 고친 날로 바꾸고 다시 올린다. 주소는 그대로라 앱 업데이트는 필요 없다.
