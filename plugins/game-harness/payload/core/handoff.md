# 작업 인계

여러 세션(Claude, Codex, 다른 PC)이 같은 프로젝트에서 일할 때, 서로 무엇을 하고 있는지 알고 멈춘 작업을 정확히 이어받기 위한 기록이다.

## 구조

```text
.game-harness/work/
├─ now/                  아직 끝나지 않은 작업. 작업 하나에 파일 하나
│  ├─ 1005-1420-lobby-ui.md
│  └─ 1005-1435-stage-data.md
└─ done/
   └─ 2026-10/
      └─ 04/             끝난 작업을 끝난 날짜별로 옮겨 둔 보관함
         └─ 1004-2210-sound.md
```

- 파일 하나는 작업 하나다. 그 작업을 잡은 세션만 그 파일을 고친다. 여러 세션이 함께 고치는 파일은 없다.
- 파일 이름은 작업 ID다. `<월일>-<시작 시각>-<짧은 영문 이름>.md` 형식으로 짓는다. 날짜와 시각은 사용자의 현지 시간이다.

## 훅이 막는 것

게임 하네스 플러그인이 설치된 환경에서는 파일을 고치기 직전에 훅이 아래를 확인하고, 어기면 수정을 거부한다. 거부되면 메시지에 이유와 해야 할 일이 나온다. 우회하지 말고 메시지대로 한다.

| 거부되는 경우 | 해야 할 일 |
| --- | --- |
| 자신의 작업 파일 없이 프로젝트 파일을 고친다 | `now/`를 읽고 자신의 작업 파일을 만든다 |
| 다른 작업의 `건드리는 곳`에 속한 파일을 고친다 | 사용자에게 묻는다 |
| 적으려는 `건드리는 곳`이 다른 작업과 겹친다 | 사용자에게 묻거나 범위를 좁힌다 |
| 다른 세션이 진행 중인 작업 파일을 고친다 | 사용자에게 묻는다 |

훅은 파일 수정 도구(Edit, Write, apply_patch 등)만 본다. 셸 명령으로 파일을 바꾸는 것은 보지 못한다. 그렇다고 셸 명령으로 훅을 피해 다른 작업의 영역을 고치지 않는다. 아래 규칙은 훅이 보지 못하는 경우에도 똑같이 지킨다.

`.game-harness/` 안의 설정(`project.yaml`), 예외(`overrides/`), 보관함(`work/done/`)은 훅이 막지 않는다.

## 언제 무엇을 하는가

### 작업을 시작하기 전

파일을 고치거나 만드는 작업은 크기와 상관없이 모두 대상이다. 검증·조사·진단만 하는 작업도 다음 세션이 이어받을 수 있으면 대상이다. 파일을 건드리지 않는 질문과 답은 대상이 아니다.

1. `now/` 폴더의 파일을 모두 읽는다.
2. 사용자의 요청이 `now/`에 있는 작업을 이어가는 것이면 그 파일을 넘겨받는다. `담당`과 `마지막 갱신`을 고치고 `다음 재개 지점`부터 시작한다. 파일을 고치는 순간 그 작업의 담당이 자신으로 바뀐다.
3. 새 작업이면 아래 "겹침 판단"을 한다.
4. 겹치지 않으면 `now/`에 자신의 작업 파일을 만든 뒤 작업을 시작한다.

사용자가 "어디까지 했어?", "마지막 작업이 뭐야?", "이어서 해줘"라고 하면 답하기 전에 `now/`를 읽는다. `now/`가 비어 있으면 `done/`에서 가장 최근 날짜 폴더의 파일을 읽어 답한다.

### 작업 중

`다음 재개 지점`이 바뀌었을 때만 자신의 파일을 고친다. 재개 지점, 남은 일, 마지막 갱신 시각을 고치고 `기록`에 한 줄을 덧붙인다. 명령 하나하나를 적지 않는다.

처음 적은 것보다 넓은 곳을 건드리게 되면, 건드리기 전에 `now/`를 다시 읽어 겹침을 확인하고 자신의 `건드리는 곳`에 추가한다. 훅은 적지 않은 곳을 고치는 것을 막지 않는다. 그래서 적어 두지 않으면 다른 세션이 그곳이 잡혀 있는 줄 모른다.

### 작업을 멈출 때

사용자가 다른 일을 시키거나, 필요한 입력이 없어 진행할 수 없으면 `상태`를 `멈춤` 또는 `막힘`으로 바꾸고 재개 지점과 이유를 적는다. 파일은 `now/`에 둔다. 멈춘 작업도 `건드리는 곳`을 계속 잡고 있으므로, 더 이어갈 일이 아니면 끝난 것으로 정리한다.

### 작업이 끝났을 때

1. `상태`를 `끝남`으로 바꾸고 완료 내용, 검증 결과, 커밋 번호를 적는다.
2. 파일을 `done/<연-월>/<일>/`로 옮긴다. 예: `done/2026-10/05/`. 폴더는 작업이 끝난 날짜다. 파일 이름은 바꾸지 않는다.
3. 작업을 커밋할 때 이 파일 이동도 같은 커밋에 넣는다. 기록만 담은 커밋을 따로 만들지 않는다.

## 건드리는 곳 적는 법

훅이 이 줄을 읽어 판단하므로 형식을 지킨다.

- 쉼표로 구분한다.
- 프로젝트 최상위 폴더 기준의 상대 경로를 `/`로 적는다. 예: `client/Assets/UI/Lobby/, data/stages.json`
- 폴더를 적으면 그 안의 모든 파일이 포함된다. 파일을 적으면 그 파일만이다.
- 고치려는 곳을 덮을 만큼만 좁게 적는다. `.`은 프로젝트 전체이며 다른 세션의 모든 작업을 막는다.
- 경로가 아닌 것(기기 빌드, 전체 검증)은 이름으로 함께 적는다. 훅은 이것을 판단에 쓰지 않지만 다른 세션이 읽는다.

아직 어디를 건드릴지 모르면 예상되는 폴더를 넓게 적고 시작한 뒤, 범위가 정해지면 좁힌다.

## 겹침 판단

자신이 하려는 일과 `now/`에 있는 다른 작업의 `건드리는 곳`을 비교한다. `상태`가 `멈춤`이나 `막힘`인 작업도 비교 대상이다.

다음 중 하나라도 해당하면 겹친다.

- 같은 파일을 고친다.
- 한쪽이 적은 폴더 안에 다른 쪽의 파일이나 폴더가 있다.
- 한쪽이 고치는 원본에서 다른 쪽이 쓰는 생성 파일이 만들어진다. 예: 데이터 원본과 그 원본에서 변환된 데이터.
- 다른 작업이 함께 쓰는 것을 오래 차지하고 있고, 자신도 그것이 필요하다. 기기 빌드, 전체 검증, 생성 자원을 지우고 다시 만드는 작업이 그렇다.

앞의 두 가지는 훅이 막는다. 뒤의 두 가지는 훅이 알 수 없으므로 직접 판단한다.

고친 것을 확인하려고 에디터나 검증을 잠깐 쓰는 것은 겹침이 아니다. 이 경우는 아래 "함께 쓰는 것의 차례"를 따른다.

겹치면 진행하지 않는다. 어느 작업과 어디가 겹치는지 사용자에게 알리고, 기다릴지, 겹치지 않는 부분만 먼저 할지, 그래도 진행할지 묻는다.

사용자가 그래도 진행하라고 하면 자신의 작업 파일에 `- 겹침 허용: <상대 작업 ID>` 줄을 넣는다. 여러 개면 쉼표로 구분한다. 사용자의 확인 없이 이 줄을 넣지 않는다.

### 담당이 없는 작업, 오래된 "진행 중"

- 담당 세션이 끝났거나 다른 PC에서 넘어온 작업 파일은 담당이 비어 있다. 그 작업의 `건드리는 곳`은 여전히 잡혀 있다. 이어서 할 작업이면 넘겨받고, 아니면 사용자에게 어떻게 할지 묻는다.
- `진행 중`인데 `마지막 갱신`이 오래됐다면 그 세션이 기록 없이 끝났을 수 있다. 짐작으로 넘겨받거나 무시하지 않는다. 사용자에게 그 작업이 아직 진행 중인지 묻는다.

## 함께 쓰는 것의 차례

엔진 에디터, 검증 실행, 데이터 동기화처럼 한 번에 한 세션만 쓸 수 있는 것은, 작업 영역이 달라도 쓰는 순간에는 차례를 지켜야 한다.

명령을 `with_lock.py`로 감싸 실행한다. 같은 이름으로 실행 중인 명령이 있으면 끝날 때까지 기다렸다가 실행된다. `project.yaml`의 검증 명령이 이미 감싼 형태로 적혀 있으면 그대로 실행한다.

  ```
  python .game-harness/harness/core/tools/with_lock.py unity-editor -- <실행할 명령>
  ```

이름은 함께 쓰는 대상마다 하나로 정해 `project.yaml`에 적어 두고 모든 세션이 같은 이름을 쓴다. 기다리다 시간이 넘으면 명령을 실행하지 않고 종료 코드 75로 끝난다. 이때는 무엇이 쓰고 있는지 사용자에게 알린다.

감싸지 않아도 되는 경우는 하나뿐이다. 프로젝트의 검증 실행기가 다른 세션의 요청이 진행 중일 때 **실패하지 않고 기다렸다가 실행한다는 것을 코드에서 확인했을 때**다. 문서에 "대기열"이라고 적혀 있다는 것만으로 판단하지 않는다. 요청이 겹칠 때 덮어쓰기만 막고 늦은 쪽을 실패시키는 실행기는 기다려 주는 것이 아니므로 감싼다. 확실하지 않으면 감싼다.

### 다른 세션의 수정이 섞인 검증

같은 폴더에서 일하는 세션들은 파일을 공유한다. 검증을 돌리면 다른 세션이 고치는 중인 내용도 함께 들어간다.

- 검증이 실패하면, 실패한 곳이 다른 작업의 `건드리는 곳`에 속하는지 먼저 본다. 속하면 자신이 고치지 않는다. 그 작업 때문일 수 있다고 사용자에게 알린다.
- 검증 결과를 보고할 때 다른 세션의 진행 중인 수정이 섞인 상태였다면 그렇다고 적는다.
- 서로의 수정이 섞이지 않은 검증이 필요하면, 다른 작업이 끝나거나 멈춘 뒤에 다시 돌린다.

## 파일 형식

줄 맨 앞의 이름(`상태`, `건드리는 곳`, `겹침 허용`)은 훅이 읽으므로 그대로 쓴다.

```markdown
# 로비 버튼 간격 수정

- 작업 ID: 1005-1420-lobby-ui
- 상태: 진행 중
- 담당: claude (2026-10-05 14:20 시작)
- 마지막 갱신: 2026-10-05 14:55
- 요청: 로비 화면 버튼 간격이 좁다. 넓혀 달라.
- 건드리는 곳: client/Assets/UI/Lobby/
- 다음 재개 지점: 간격 수정은 끝났다. 에디터에서 화면을 눈으로 확인하는 것부터 한다.
- 남은 일: 화면 확인, 커밋
- 주의사항: 상점 버튼은 다른 프리팹을 공유하므로 건드리지 않았다.

## 기록

- 14:20 시작. 간격 값이 LobbyLayout 프리팹에 있는 것을 확인.
- 14:55 간격 수정 완료. 컴파일 확인.
```

`상태`는 `진행 중`, `멈춤`, `막힘`, `끝남` 중 하나다. 끝난 파일에는 아래 항목을 더한다.

```markdown
- 완료 내용: 버튼 간격 12에서 20으로 수정.
- 검증: 컴파일 통과. 에디터에서 로비 화면을 눈으로 확인.
- 커밋: a1b2c3d
```

## 적지 않는 것

- 비밀값, 인증 정보, 개인정보
- 긴 원문이나 도구 출력 전체
- 명령 하나하나의 실행 내역
- 커밋 기록을 그대로 옮긴 변경 목록. 변경 이력의 기준은 git이다.

## 기록과 실제가 다를 때

실제 파일과 git 상태를 우선한다. 차이를 자신의 작업 파일 `기록`에 적는다. 다른 세션의 파일은 고치지 않는다.
