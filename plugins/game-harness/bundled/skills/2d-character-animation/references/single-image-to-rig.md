# From one image to a working Unity 2D skeletal asset

Use this mode for an attached image, local path, or direct image URL. The required result is a deforming, animated Unity asset, not a tutorial. Use the [official rigging reference](official-rigging.md) for the matching Editor and package workflow; official samples are examples to inspect when needed, not substitutes for the user's image.

## Intake and art construction

1. Resolve the image address, fetch the image if it is remote, inspect its pixels, dimensions, transparency, pose, and visible joints, and save an unchanged source copy. If the address is a web page rather than an image file, identify the actual source image before using it. Keep source and generated art separate so the result can be revised.
2. Find the target Unity project from the active Editor or workspace. Follow its asset paths and scene conventions. If none exists, create a small isolated 2D demo project with an available compatible Editor. Do not treat a generic Unity sample project as the deliverable.
3. Prefer the visibility-map method ([visibility-map-rig.md](visibility-map-rig.md)), which builds on the decomposition method ([layered-illustration-rig.md](layered-illustration-rig.md)). If the image already shows the full character in an animatable pose, cut its layers in place. If it is cropped or awkwardly posed, first obtain one finished full-body illustration that preserves the design, register it to the original to check proportions, and cut layers from that. **Invented body parts must keep the source's viewing angle and stance** (Estelle v012 → v013): the source portrait showed a three-quarter torso; the generated lower body stood square to the viewer (front knee facing out, both legs straight), so the figure read as twisted at the waist and every later layer inherited it. Before accepting the full-body art, write down the angle cues of the visible part (face and torso centre-line direction, shoulder line, hip line) and check the invented part against them: hip line and skirt centre follow the torso turn, the front knee and feet point the same way as the torso, the back leg is partly hidden by the front one, and the two legs have different shapes — the weight-bearing back leg stands straight, only the free front leg bends (Estelle v013: both legs drawn with the same bend read as a copy). Keep everything that the source shows pixel-identical (composite it back over the generation and measure the difference outside the invented area). Separately generated parts assembled into a body are the fallback, not the default.
4. Choose a rig structure from the image. A snake, ribbon, tail, or other continuous form may use one skinned sprite and a chain of bones. An articulated person or creature usually needs separate transparent RGBA parts (torso, head, upper/lower limbs, hands/feet as visible), overlapping painted pixels behind joints, and a shared skeleton. Keep each part registered to the original canvas so the assembled neutral pose matches the source. Crop or erase background only where the intended character boundary is clear; inspect the result at the display scale.
5. If the flattened image hides a limb or has no pixels behind a shoulder, elbow, hip, or knee, create the missing art needed for the requested movement. Use an image-generation or inpainting tool for visual repainting or extension when the session has one (`imagegen` in Codex), inspect its output, and preserve the source. Without one, use the refill methods in [layered-illustration-rig.md](layered-illustration-rig.md#4-refill-what-moving-layers-will-reveal) and keep motions within what the refills can support. Where the unseen design is materially ambiguous, ask for that specific design decision while building the visible parts. Avoid promising a clean extreme pose from pixels that do not exist.

## Unity assembly and animation

1. Inspect Editor and package versions; install only required packages through the Editor's Package Manager API when authorized. Follow `unity-cli` to target the right Editor and `unity-package-management` for package changes. Do not hand-edit sprite `.meta`, scene, prefab, or package manifest files to simulate a rig. Use the Editor and version-compatible sprite data provider APIs or Skinning Editor for bones, geometry, and weights; apply `sprite-editor` if changing importer pivots, rectangles, or outlines.
2. For a decomposition rig, build with `../scripts/unity/LayeredRigBuild.cs` (`Build`, then `Verify`) from the exported `rig.json`/`anim.json`; it drives the same sprite data provider APIs. Otherwise, import derived transparent parts with consistent scale and pivots. For a layered `.psb` use PSD Importer and its character rig workflow; separate PNG parts need no PSD Importer. Build a bone hierarchy aligned to joints, generate geometry, bind only relevant bones, and correct weights at bends. The rig must visibly deform at least one intended joint; use rigid Transform animation only where the art calls for it.
3. Create the prefab in the scene, ensure deforming sprites have `Sprite Skin` and correctly mapped Root Bone/bone Transforms, and save it. Make requested clips, or default to a looping idle plus one visible joint-motion demonstration appropriate to the subject. Assign clips to an Animator Controller and attach it to the prefab. Add a preview scene or use a suitable existing scene so the result can be opened and played immediately.
4. Test several poses, clip playback, and Animator transitions in the actual Editor. Inspect arm/leg seams, image stretching, unexpected bone influence, part ordering, camera scale, and console errors. If available, inspect Play mode visually or capture a short preview. Then run the build → review → fix loop in [review-protocol.md](review-protocol.md) with an independent reviewer. Fix visible defects before delivery; if one-image ambiguity limits a movement, state exactly which joint/pose and retain the best working motion.

## Completion evidence

Report the source image path, derived part assets, prefab, clips, controller, and scene. Confirm the Editor/package versions, that Sprite Skin has live bone bindings, that the clips move those bones and deform the sprites, and that the preview scene plays without relevant errors. Distinguish actual Editor/visual checks from files merely created on disk. Do not call a one-frame sprite, loose bones, or an untested prefab a completed skeletal animation.
